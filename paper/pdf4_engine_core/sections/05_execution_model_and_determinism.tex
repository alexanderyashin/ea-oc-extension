\section{Execution Model and Determinism}

This section specifies the execution model of the Engine Core strictly as a
\textbf{diagnostic-only} evaluator.
It \textbf{excludes} any notion of process orchestration, workflow control,
scheduling, runtime management, or operational governance.

\subsection{Run lifecycle}

A single kernel run is defined as one atomic evaluation:
\[
(S,\;\mathcal{I},\;\Theta,\;M)\;\Rightarrow\;R
\]
where $M$ denotes explicit execution metadata
(e.g.\ version identifiers or environment descriptors).
Such metadata is recorded for traceability \textbf{only} and
\textbf{must not} influence evaluation, classification, STOP semantics,
or provenance identity.

There is exactly one input bundle and exactly one result.
The Engine Core \textbf{does not} manage sessions, pipelines, retries,
recovery, or long-lived execution contexts.

\paragraph{No internal lifecycle (invariant).}
The kernel has \textbf{no} notion of \emph{start}, \emph{progress},
or \emph{completion} beyond the existence of the evaluation result $R$
or a terminal STOP.
Any higher-level lifecycle management is external and
\textbf{non-normative} with respect to OPS-1.

\subsection{Determinism as architectural invariant}

OPS-1 fixes determinism as an \textbf{architectural invariant} of the kernel.
Determinism is \textbf{not} a best-effort execution property,
\textbf{not} a process guarantee,
and \textbf{not} a toolchain attribute.
It is a necessary and non-negotiable condition for OPS-1 conformance.

\paragraph{Deterministic domains (invariant).}
For identical declared inputs $(S,\mathcal{I},\Theta,M)$,
the kernel \textbf{must} yield an identical result $R$
in all of the following domains:
\begin{itemize}
  \item \textbf{Diagnostic result determinism:}
        identical admissibility classification and identical diagnostic outputs.
  \item \textbf{Operation graph traversal determinism:}
        traversal and evaluation order are determined solely
        by declared structures.
  \item \textbf{STOP detection determinism:}
        terminal STOP recognition is deterministic and input-complete.
  \item \textbf{Provenance assignment determinism:}
        attribution of outputs to declared inputs and referenced artefacts
        is deterministic.
  \item \textbf{Registry state determinism (logical):}
        registry evolution is append-only and order-stable
        in the logical sense of reference introduction.
\end{itemize}

Any deviation in any of these domains \textbf{violates} OPS-1 determinism.

\paragraph{What determinism does \emph{not} mean (descriptive).}
Kernel determinism \textbf{does not} imply:
\begin{itemize}
  \item predictability of future states of the diagnosed system;
  \item stability of the system over time;
  \item repeatability of real-world observations;
  \item causal explanation, attribution, or forecasting of outcomes.
\end{itemize}

Determinism is solely a property of admissibility evaluation
within the kernel boundary.

\subsection{Bounded non-determinism (strictly cosmetic)}

OPS-1 permits non-determinism \textbf{only} where it has
\textbf{no semantic impact} on diagnostic results,
terminal STOP evaluation, provenance identity,
or registry meaning.

\paragraph{Permitted (strictly bounded).}
The following are permitted \textbf{only if}
they are demonstrably semantics-free:
\begin{itemize}
  \item ordering of physically independent artefacts,
        \textbf{if and only if} ordering has no effect
        on diagnostic meaning;
  \item rendering and layout properties
        (purely cosmetic presentation);
  \item non-normative metadata
        that does not influence evaluation semantics.
\end{itemize}

\paragraph{Forbidden (disqualifying).}
Any non-determinism is \textbf{forbidden}
if it can influence:
\begin{itemize}
  \item diagnostic outputs or admissibility classification;
  \item terminal STOP recognition or NO-GO evaluation;
  \item provenance assignment or traceability links;
  \item selection of execution paths by heuristic,
        adaptive, or conditional logic;
  \item time-, load-, or environment-dependent behavior
        with semantic impact.
\end{itemize}

If such non-determinism is present or required,
OPS-1 conformance is \textbf{violated}.

\subsection{No hidden state rule}

The Engine Core \textbf{must not} depend on hidden
or mutable internal state.

\paragraph{Explicitly forbidden (prohibition).}
\begin{itemize}
  \item caches that affect evaluation results;
  \item learned parameters or adaptive thresholds;
  \item implicit memory across runs;
  \item time-dependent behavior not represented in inputs.
\end{itemize}

Any dependency not explicitly represented in
$(S,\mathcal{I},\Theta,M)$ \textbf{invalidates}
OPS-1 conformance.

\subsection{Environment independence (semantic)}

The kernel is environment-independent
in a \emph{semantic} sense:
\begin{itemize}
  \item evaluation semantics \textbf{must not}
        depend on wall-clock time;
  \item evaluation semantics \textbf{must not}
        depend on execution order of prior runs;
  \item evaluation semantics \textbf{must not}
        depend on external services or side effects.
\end{itemize}

This constraint applies exclusively to kernel semantics.
It imposes \textbf{no} requirements on build tooling,
containers, deployment environments, or infrastructure,
all of which are external to OPS-1.

\subsection{No execution control semantics}

The Engine Core admits \textbf{no} execution control
semantics of any kind.
In particular, it does \textbf{not} admit:
\begin{itemize}
  \item pause, resume, or step-wise execution;
  \item conditional branching or scenario switching;
  \item fallback, degraded, recovery,
        or continuation modes.
\end{itemize}

Execution yields exactly one admissible outcome:
either a result $R$ or a terminal STOP.
No admissible third state exists.
