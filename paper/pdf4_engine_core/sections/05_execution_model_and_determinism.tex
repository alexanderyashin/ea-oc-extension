\section{Execution Model and Determinism}

This section specifies the execution model of the Engine Core strictly as a
\textbf{diagnostic evaluator}. It intentionally excludes any notion of process
orchestration, workflow control, scheduling, or runtime management.

\subsection{Run lifecycle}

A single kernel run is defined as an atomic evaluation:
\[
(S,\;\mathcal{I},\;\Theta,\;M)\;\Rightarrow\;R
\]
where $M$ denotes explicit execution metadata (e.g.\ version identifiers or
environment descriptors) that are recorded for traceability but do not influence
evaluation semantics.

There is exactly one input bundle and exactly one result. The Engine Core does not
manage sessions, pipelines, retries, or long-lived execution contexts.

\paragraph{No internal lifecycle.}
The kernel has no notion of \emph{start}, \emph{progress}, or \emph{completion}
beyond the existence of the evaluation result $R$ or a terminal STOP.
Any higher-level lifecycle management belongs to external tooling.

\subsection{Determinism as architectural invariant}

OPS-1 fixes determinism as an \textbf{architectural invariant} of the kernel.
Determinism is not a best-effort execution property, not a process guarantee, and
not a toolchain attribute. It is a necessary condition for OPS-1 conformance.

\paragraph{Deterministic domains (non-negotiable).}
For identical declared inputs $(S,\mathcal{I},\Theta,M)$, the kernel must yield an
identical result $R$ in the following domains:

\begin{itemize}
  \item \textbf{Diagnostic result determinism:} identical admissibility classification and identical diagnostic outputs.
  \item \textbf{Operation graph traversal determinism:} traversal and evaluation order are determined solely by declared structures.
  \item \textbf{STOP detection determinism:} STOP / NO-GO recognition is deterministic and input-complete.
  \item \textbf{Provenance assignment determinism:} attribution of outputs to declared inputs and referenced artefacts is deterministic.
  \item \textbf{Registry state determinism (logical):} registry evolution is append-only and order-stable in the logical sense of reference introduction.
\end{itemize}

Any deviation in these domains constitutes a violation of OPS-1 determinism.

\paragraph{What determinism does \emph{not} mean.}
Kernel determinism does not imply:
\begin{itemize}
  \item predictability of future states of the diagnosed system;
  \item stability of the system over time;
  \item repeatability of real-world observations;
  \item causal explanation or forecasting of outcomes.
\end{itemize}

It is solely a property of admissibility evaluation within the kernel boundary.

\subsection{Bounded non-determinism (strictly cosmetic)}

OPS-1 permits non-determinism \emph{only} where it has no semantic impact on any
diagnostic result, STOP evaluation, provenance attribution, or registry meaning.

\paragraph{Permitted (strictly bounded).}
The following are permitted only if they are demonstrably semantics-free:

\begin{itemize}
  \item ordering of physically independent artefacts, \emph{if and only if} ordering has no effect on diagnostic meaning;
  \item rendering and layout properties (purely cosmetic presentation);
  \item non-normative metadata that does not influence evaluation semantics.
\end{itemize}

\paragraph{Forbidden (disqualifying).}
Any non-determinism is forbidden if it can influence:

\begin{itemize}
  \item diagnostic outputs or admissibility classification;
  \item STOP / NO-GO evaluation or terminal recognition;
  \item provenance assignment or traceability links;
  \item selection of execution paths (heuristic, adaptive, or conditional by non-declared factors);
  \item time-, load-, or environment-dependent behavior with semantic impact.
\end{itemize}

If such non-determinism is present or required, OPS-1 conformance is violated.

\subsection{No hidden state rule}

The Engine Core must not depend on hidden or mutable internal state.

\paragraph{Explicitly forbidden.}
\begin{itemize}
  \item caches that affect evaluation results;
  \item learned parameters or adaptive thresholds;
  \item implicit memory across runs;
  \item time-dependent behavior not represented in inputs.
\end{itemize}

Any dependency that is not explicitly represented in $(S,\mathcal{I},\Theta,M)$
invalidates OPS-1 conformance.

\subsection{Environment independence (semantic)}

The kernel is environment-independent in a \emph{semantic} sense:
\begin{itemize}
  \item evaluation semantics must not depend on wall-clock time;
  \item evaluation semantics must not depend on execution order of prior runs;
  \item evaluation semantics must not depend on external services or side effects.
\end{itemize}

This requirement does not impose constraints on build tooling, containers, or
deployment environments, which are external to kernel semantics.

\subsection{No execution control semantics}

In particular, it does not support:
\begin{itemize}
  \item pause, resume, or step-wise execution;
  \item conditional branching or scenario switching;
  \item fallback, degraded, or recovery modes;
\end{itemize}

Execution either yields a result $R$ or terminates at STOP. No admissible third
state exists.
